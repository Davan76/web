# 學習字卡網頁流程（可套用到任何主題）

> **最後更新：2026-11-19**
> **用途**：給使用者本人，以及之後接手的對話照著做。
> **適用範圍**：可以拆成「詞條 + 解釋 + 例句 + 分類」的學習內容（語言、專業術語等）。法規條文、產品規格等非這種結構的主題，不適用本流程。

這份流程來自「多益單字字卡」專案。換成其他主題（例如日文、商業術語、醫學詞彙）時，照同樣順序做即可。

## 前提條件
- 本機需安裝 Node.js 與 Playwright（測試用）；Python 3 與 `cmudict` 套件（發音用）。
  - 指令（以你的系統為準）：在專案資料夾執行 `npm i playwright && npx playwright install chromium`（測試檔用 `require` 載入，需裝在專案內）；`pip install cmudict`。
- 發布需要 GitHub 帳號與 GitHub Pages；沒有的話可改用其他靜態網站服務。
- 授權：每個來源都要先查證授權條款，不能只憑印象寫（做法見第 9 步）。

## 0. 先決定的事（每次開新主題都要問清楚）
- **主題與範圍**：學什麼？單字、片語、句型、還是其他？
- **來源**：資料從哪裡來？是公開資料集、自己的清單，還是網路文章？
- **授權**：來源是否允許公開再散佈？是否允許商業使用？
- **分類方式**：依什麼分單元（例如難度、場景、詞性）？
- **卡片欄位**：每張卡要顯示哪些資訊？（參考「第 3 步」）

## 1. 取得來源資料
- 先確認網路能連到來源；連不到時，申請白名單或請使用者上傳檔案。
- 把原始檔案保存下來（例如 `data_src/`），不要只存處理後的結果。
- 記錄來源網址、下載日期、授權條款。

## 2. 清理與篩選
- **先用小樣本試跑**：先用 20–30 筆跑完整流程，確認格式與規則都正確，再全量處理。（理由：全量才會暴露的錯誤很多，容易被跳過。）
- 寫下篩選規則（例如：只留單一詞、去除重複、去除空白列）。
- 每條規則都要能用數字驗證（例如「去掉 1,456 筆片語，剩 9,698 筆」）。
- 規則由使用者確認；不確定的地方列出來問，不自己猜。
- **人工抽查**：隨機抽樣（例如 40 筆），不挑好看的看。抽樣結果記錄抽了幾筆、哪些錯。（理由：只看挑出來的好樣本，會高估品質。）

## 3. 產生卡片內容
每張卡建議固定格式（可依主題調整）：
```
音標或發音（如適用）
詞性：
中文翻譯：
變化形：
搭配詞（最多 2 組）：
例句（英文 + 中文）：
```
- **不編造事實**：資料沒有的欄位就留空或省略，不用模型知識補。
- 需要自己撰寫的內容（例句、中文說明）要在頁面與文件中標示「本專案自行撰寫」。
- 來自模型知識的推測要標記，例如「字源推測」。

## 3.5 誠實度原則
- 宣稱的正確率或覆蓋率，必須附上抽樣數與方法。沒有抽查，就不寫數字。
- 模型知識產生的內容，一律標記，並說明未經外部驗證。

## 4. 發音與其他自動化資料（如適用）
- 英文發音：用 CMUdict 查詢後轉成 IPA，查不到就不顯示。
- 其他語言：需要另找來源，不能直接套用英文的工具。

## 5. 做成單一 HTML 網頁
- 一個檔案即可離線開啟，不需要後端。
- 內嵌資料、SRS 四段評級（Again / Hard / Good / Easy）、進度保存在瀏覽器。
- **提醒使用者**：瀏覽器進度會因清除資料、換裝置而消失，無法跨裝置同步。
- 單元選單依分類產生；選單字數從資料自動計算。
- 手機與電腦分別測試版面。

## 6. 測試（每次發布前都要跑）
- **標準**：電腦與手機的完整自動測試全部通過才能發布。只跑部分測試不算。
- 用自動化測試（Playwright）檢查：字數、各單元字數、版本號、評級行為、重新整理後進度、JavaScript 錯誤。
- 測試時從檔案讀取預期值，不寫死數字。
- 測試要能抓到錯誤：故意改錯版本號，確認測試會失敗。
- 舊版進度升級：用舊版建立進度，再開新版檢查。

## 7. 版本與紀錄
- 版本規則：小改款用小數點（Ver.1.1、Ver.1.2），大改款進位整數（Ver.2）。
- 每次發布都更新 `CHANGELOG.md`，寫清楚改了什麼、資料來源是什麼。

## 8. 發布與隱私
- 若加入第三方追蹤或計數（例如 GoatCounter），網頁底部要有隱私說明，寫清楚收集什麼、用途為何。
- 不在前端儲存或傳送個人可識別資料；IP 等資料只能在伺服器端以雜湊處理。
- 推送到 GitHub（GitHub Pages）。
- 打包完整專案 zip 給使用者。
- 上線後實際打開網頁確認版本號與功能。

## 8.5 交接（換對話或換人時）
- 寫清楚：目前版本號、最新 commit、哪些檔案是最新的、哪些還沒完成、待確認的問題。
- 下次接手前，先讀 `CHANGELOG.md` 與本文件，再動手。

## 9. 授權與來源檢查（發布前）
- 開新主題時，先查來源的授權條款，把摘要給使用者，使用者確認後才處理資料。
- 列出所有來源的授權。若有 CC BY-NC-SA 等限制，整體授權要跟著符合，不能標「All rights reserved」。
- 來源沒有授權說明的，先標示「授權未確認」，並請使用者確認。
- 作者與版權標示寫一次即可。
- 來源沒有授權的資料，不應該公開散佈，要先取得許可或更換來源。

## 10. 需要使用者確認的事（每次都要問）
以下決定由使用者決定；技術細節我可以直接做，事後告知。
- 來源是否可用、授權是否允許。
- 分類與單元名稱。
- 卡片欄位與顯示位置。
- 版本號與發布時間。

## 工具與檔案（以本專案為例）
- `convert_toeic.py`：資料轉換成卡片 CSV 與網頁資料。
- `build_ipa.py`：用 CMUdict 產生音標。
- `affixes.py`：字首字根字尾與字源（僅示範，換主題時重寫）。
- `tests/smoke_test.js`：版本無關的自動測試。
- `CHANGELOG.md`：版本紀錄。

## 常見錯誤（本專案踩過的）
- 用 `toLowerCase()` 當鍵，會讓同拼法的不同卡片互相覆蓋（例如 hand 與 HAND）。原則：用來當鍵的欄位，先用真實資料檢查是否唯一，再決定用哪個欄位。
- 網頁的進度會保存舊卡片內容，改版後要同步更新卡片內容。
- 字根拆解借用同形的單字解釋，容易誤導，要檢查上下文是否相符。
- 瀏覽器的 CORS 與白名單：外部服務要先確認網域可連。
